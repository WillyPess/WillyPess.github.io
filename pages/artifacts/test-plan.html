Test Plan, FinanceHUB

Sample artifact, portfolio demonstration

FinanceHUB is a full-stack personal finance application (React frontend, Express REST API, SQL database, JWT authentication with refresh tokens) built to serve as a realistic target for QA automation practice. This document is a condensed, ISTQB-style test plan illustrating how I approach planning for a project of this size. It is not tied to a live release and exists purely to demonstrate my documentation process.

1. Introduction & objectives

This plan defines the scope, approach, resources and schedule of testing activities for FinanceHUB. The primary objective is to verify that core financial workflows, authentication, transaction management, subscriptions, debts, investments and monthly summaries, behave correctly, securely and consistently with the underlying data, before any release is considered ready.

Secondary objectives are to establish a repeatable regression suite (Cypress E2E and API tests), catch data-integrity issues at the SQL layer early, and produce evidence (reports, logs, screenshots) that supports fast triage when defects are found.

2. Scope

In scope

  • User registration, login, JWT access and refresh token flow, logout
  • Transactions: create, edit, delete, list, filter
  • Subscriptions: recurring charge tracking and renewal dates
  • Debts: balance tracking and repayment schedules
  • Investments: holdings and valuation display
  • Monthly summary calculations and aggregation
  • REST API contract validation (status codes, payloads, auth headers)
  • SQL-level data-integrity checks against API/UI results

Out of scope

  • Third-party payment gateway internals (mocked in test environment)
  • Load/performance testing beyond smoke-level checks
  • Native mobile app (web-only application)
  • Infrastructure/deployment pipeline testing

3. Test strategy & levels

A layered strategy is used so that failures are caught as close as possible to their source.

  • End-to-end (Cypress): user-facing flows exercised through the React UI: login, token refresh on expiry, transaction CRUD, subscription/debt/investment management, and monthly summary rendering. Page objects and Faker.js-generated data keep suites maintainable and independent of fixed data.
  • API validation: direct testing of the Express REST endpoints (Postman/automated scripts) for authentication, authorization, status codes, response schemas, and edge cases (expired tokens, invalid payloads, unauthorized access to another user's data).
  • SQL data-integrity checks: queries run against the database after UI/API actions to confirm that what is persisted matches what is displayed, particularly for calculated fields such as monthly summaries, running balances and subscription renewal dates.

4. Risk analysis

Risk areaDescriptionImpactMitigation
Auth & session handling Refresh token not rotated or expired token accepted, allowing session hijack or unwanted logout High Dedicated E2E and API tests for token expiry, refresh, and revocation paths
Transaction integrity Concurrent edits or deletions cause lost updates or duplicate entries High API-level negative tests plus SQL checks for orphaned/duplicate records
Calculation accuracy Rounding or aggregation errors in monthly summaries (see linked bug report sample) Medium Cross-check UI totals against SQL aggregate queries for each test period
Authorization boundaries A user able to view or modify another user's financial data via API High Explicit cross-account API tests using two seeded test users

5. Test environment

  • Dedicated staging environment with a seeded, isolated SQL database, never shared with production data
  • Backend: Node.js / Express REST API, JWT auth (access and refresh tokens)
  • Frontend: React, served via a Dockerized environment for repeatable local and CI runs
  • Test data generated with Faker.js to avoid dependence on hand-crafted fixtures
  • Cypress for E2E, Postman/Newman for API, direct SQL client for data-integrity queries

6. Entry & exit criteria

Entry criteria

  • Feature branch deployed to the staging environment
  • Test environment seeded and reachable (API and DB healthy)
  • Test cases reviewed and mapped to acceptance criteria

Exit criteria

  • 100% of planned E2E and API test cases executed
  • No open high-severity defects
  • SQL data-integrity checks pass for all in-scope features
  • Known medium/low defects logged with agreed follow-up

7. Deliverables

  • This test plan document
  • Cypress E2E automated test suite and execution report
  • API test collection (Postman/Newman) and results
  • SQL data-integrity check scripts
  • Defect reports for any issues found, see the sample bug report
  • Test summary report at exit
