Bug Report, FinanceHUB

Sample artifact, portfolio demonstration

A realistic defect report for FinanceHUB, formatted the way I document bugs in JIRA/TestRail: clear reproduction steps, expected vs. actual results, severity/priority classification and a root-cause hypothesis to speed up developer triage.

ID

FHUB-214

Title

Monthly expense summary total does not match sum of individual transactions when a transaction is edited mid-month

Severity

High

Priority

P2, fix before next release

Environment

Staging, Chrome 126, FinanceHUB build 2026.03.11, PostgreSQL 15

Preconditions

User is logged in with a seeded test account that has at least 5 expense transactions recorded in the current month, and the "Monthly Summary" widget has already been viewed once (cached).

Steps to reproduce

1. Log in and open the Dashboard, noting the "Monthly Expenses" total shown in the summary widget.
2. Navigate to Transactions and edit the amount of an existing expense transaction from the current month (e.g. change $45.00 to $67.50).
3. Save the change and return to the Dashboard without a full page reload (use in-app navigation).
4. Compare the "Monthly Expenses" total shown against the actual sum of all listed transactions for the month.

Expected result

The Monthly Expenses total updates immediately to reflect the edited transaction and equals the sum of all expense transactions for that month.

Actual result

The Monthly Expenses total still reflects the pre-edit amount until the page is fully reloaded (F5). A direct SQL query against the transactions table confirms the underlying row was updated correctly. The discrepancy is isolated to the cached summary value shown in the UI.

Evidence

Screenshot of Dashboard before/after edit (pre-reload) attached in JIRA ticket FHUB-214. SQL query used for verification: SELECT SUM(amount) FROM transactions WHERE user_id = :id AND type = 'expense' AND date_trunc('month', occurred_at) = date_trunc('month', now()); Result matched the expected total, confirming the API/DB layer is correct and the defect is front-end state management only.

Root-cause hypothesis

The Dashboard summary widget appears to cache the monthly aggregate in client-side state on first load and does not invalidate that cache when a transaction is edited elsewhere in the app. Only a full reload re-fetches the aggregate from the API. Likely fix: invalidate/refetch the summary query on any transaction mutation (create, edit, delete), e.g. via a shared query cache key or event bus.

Status

Open, assigned for triage
